## What this wave taught

- **L-35** (60%) Every way a binary is built needs the same provenance check: the image build had no .git and no check, so it shipped unknown while the archives were verified
  - from FEAT-144 · ghcr.io/startr-trade/kanbanr:v0.1.0 printed (unknown, built unknown)
- **L-34** (60%) A workflow step make ci cannot run is still checkable: run its script in the same container image, under the shell GitHub will use (sh in a container job, not bash)
  - from FEAT-143 · v0.1.0 verify-install used ${GITHUB_SHA:0:12}; dash stopped with Bad substitution; actionlint shellchecks as bash and passed it
- **L-33** (60%) Never judge a command's result by the exit status of a pipeline it feeds — 'cmd | tail' reports tail's status; read the command's own output or use set -o pipefail
  - from FEAT-130 · make codeql was run as 'time scripts/security-scan.sh codeql 2>&1 | tail -40'; exit 0 was read as 0 findings and recorded, while the JavaScript scan had found the XSS that GitHub then reported
- **L-32** (60%) When a change alters what a shared helper returns, grep the tests for the old behaviour too — a test that builds its expected value the old way fails only on the platform where the two differ
  - from FEAT-129 · normalize() stopped returning Windows' \\?\ prefix; five core tests built their expected paths with raw canonicalize, which still does — invisible on Linux, red on Windows
- **L-31** (59%) Run every CI workflow's checks locally before calling work ready to push — a check no local command reproduces is where 'passes here' and 'red on GitHub' part ways
  - from FEAT-129 · the first GitHub runs failed four ways that all passed locally: a monitor test against a binary built without web/dist, a macOS symlinked temp path, a Windows link error, and a mirrored changelog chapter that only docs.yml compared with its source (hand-edited, 213 lines behind)
- **L-8** (57%) Dogfood the layout you recommend — `kanbanr where` had been suggesting the sibling board folder to every user while this project itself sat on the legacy one
  - from FEAT-024 · the board lived at <repo>/data, protected only by a gitignore line, until it was moved to ../kanbanr.kanbanr; the tool's own `suggested_data_dir` had named that path all along

## What we make of it

_Written by whoever writes it, from the numbers above. It may explain them, and it may disagree with what we expected — it may not contradict them._

MS-002 took kanbanr from a working tool to a public one: open-sourcing, CI on three operating
systems, security scanning, branding, the one-step install, and the v0.1.0 and v0.1.1 releases.
That is why scope nearly doubled (17 → 32). The eight items added without a recorded cause came
from the open-sourcing work itself: screenshots, the README, session summaries, the embedded skill
and the second release. Recording an origin for added items, as defects already carry, would make
the next wave's scope line say why it grew.

All six defects were found at the publishing edge (CI, code scanning, the plugin validator, the
release run), not by the local suite. The three that escaped share one shape: something built or
run a second way that no local check exercised — the plugin manifest, a container step run by
dash, the image built without `.git` or `skill/`. L-31, L-34 and L-35 are that one lesson met three
times, and `make ci` now has a check for each case. The three reworked items (FEAT-130, FEAT-133,
FEAT-140) were reopened the same day they were called done, by evidence that arrived afterwards;
for FEAT-130 the cause was reading a pipeline's exit status as the command's (L-33).

The cycle-time spread (p50 22m, p90 12h) is the split between small fixes finished in one sitting
and release items that waited on the maintainer's checks and pushes. Every requirement (56/56)
ended proven by a green test. Sixteen older items have no recorded moves: they predate flow
tracking, so they say nothing about this wave's flow.
