## What this wave taught

- **L-23** (74%) Recognise a token with its boundary, never as a substring. Three defects on this board are the same mistake: [no-ref] matched in prose so a commit explaining the escape was read as taking it (FEAT-056); a test name's / was passed into a route by a whole-path encoder used on one segment (FEAT-079); and the commit guard found '-m' anywhere in a command line, refusing correct commits and blocking a Python script that merely mentioned the flag (FEAT-082). Writing the rule down after the first one did not stop the next two — so when parsing anything out of free text, state what the boundary is before writing the match.
  - from FEAT-082
- **L-28** (60%) Never chain commit and merge after a test run in one command: the suite reported 2 failures and the merge went ahead anyway
  - from FEAT-105
- **L-27** (60%) The capture hook records nothing when a test run is wrapped (rtk proxy cargo test): feed the output to kanbanr capture, or run cargo test bare
  - from FEAT-101
- **L-25** (59%) Fix every instance of a bug, not the one that bit you. FEAT-082's first fix scoped inline_message to the git commit invocation and left the hook-skipping check two lines above it still scanning the whole command line — so a message explaining '[ -n $x ]' was read as passing -n, and the commit was refused. The second failure looked like a new bug and was the same one. When a defect is 'a token matched without its boundary', grep for every other match of that shape in the same function before calling it done.
  - from FEAT-082
- **L-24** (59%) A guardrail must be observed failing before it counts — twice in one session a check I wrote passed against the exact bug it was written for. check:ui's first affordance rule compared class names while .btn and .chip shared a background; its first duplicate-link rule used <Link[^>]*> which stops at the > inside className={({isActive}) => ...}, so it matched nothing at all and reported success. Both were caught only by deliberately reintroducing the defect. ADR-0008 makes the revert part of writing the check.
  - from FEAT-083
- **L-22** (59%) Write the requirement as the property the user needs, not as the shape of the fix. FEAT-076/R-2's test was "no action element carries the chip class" — so changing the class satisfied it while the button still looked exactly like a tag, and the user reported the same complaint twice. The property was "recognisable as a control without hovering"; .btn and .chip had always declared the same background, which nothing compared. A test written from the fix passes on the next instance of the same bug.
  - from FEAT-081
- **L-21** (59%) A greppable rule belongs in a script, not a review habit. FEAT-076's fix was a one-word class change; what makes it stay fixed is `npm run check:ui`, which fails on a button styled as a chip and on a chip with an onClick. It catches the exact regression that shipped, from both directions, and the next reintroduction looks perfectly ordinary in a diff without it.
  - from FEAT-076
- **L-20** (59%) When a second surface produces the same record as an existing one, make it read the first one's source — do not write an equivalent. Three of the four defects in this review were that: the monitor invented an approver string instead of reading the commit identity `kanbanr approve` resolves; the review queue invented a scope filter instead of reusing the gate `doctor` had; and the test-state caller picked the whole-path encoder while the route it targets documented needing the segment one. Each looked correct in its own diff.
  - from FEAT-077

  - from FEAT-075 · deferring FEAT-074 was refused for want of an approval; the alternatives were approving work nobody intended to start or recording an --unapproved reason for a deliberate parking

## What we make of it

_Written by whoever writes it, from the numbers above. It may explain them, and it may disagree with what we expected — it may not contradict them._

- **This wave grew from 12 planned items to 45**, and the growth is mostly defects: 23, 19 of them found after the work was called done. Most trace back to items in the same wave. The commit guard (FEAT-056) alone fathered four (FEAT-082, 086, 098, 108), each a case of text in a command being read as a command. That is the pattern to remember: a guardrail that parses free text keeps meeting new text (L-3).
- **Ten additions have no recorded cause.** They were requests made during the wave, such as the setup interview, session summaries, ratify from the Review page and the summary exclusion list. They are genuine scope added by the user, not unexplained growth. Recording them with a cause (for example, a label) would let the retro say so.
- **Cycle time spans minutes to 2.5 days.** Short times are bookkeeping; the long tail is the method's own items, which took real design.
- **FEAT-067 finished with 5 unproven requirements.** It is the one gap in 125/130, and the reason should be recorded or the tests flipped.
- **What changed as a result:** gates, sign-offs and presets (MS-007) came directly from finding that the start gate, finish and auto-advance assumed one shape of work.
